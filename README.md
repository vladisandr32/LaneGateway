# LaneGateway

**Прозрачный AI-роутер с visual-конструктором правил.**

LaneGateway принимает запрос из любого клиента (бот, CLI, веб), сам решает,
какие модели и инструменты нужны под конкретную задачу и бюджет, и показывает
пользователю весь путь этого решения — какая модель выбрана, почему, из каких
модулей собран ответ и сколько это стоило. Все правила маршрутизации
настраиваются через GUI, без правки конфигов или кода.

## Зачем это, если уже есть LiteLLM / OpenRouter / OmniRoute

Эти проекты решают задачу "получить доступ к множеству LLM через один
эндпоинт" — и делают это хорошо, с большим количеством провайдеров и
стратегий. LaneGateway не соревнуется с ними в количестве.

Разница в философии:

- **Explainable** — любое решение роутера можно открыть и увидеть цепочку:
  что проверено → какой инструмент вызван → почему выбрана эта модель →
  сколько это стоило. Не чёрный ящик и не строка в консольном логе.
- **Configurable через GUI, а не конфиг-файл** — подключить модуль (например,
  свой SearXNG), сменить модель, поменять порог по цене — всё через
  интерфейс, без перезапуска сервера и без правки YAML/кода.
- **Replayable** — история решений сохраняется, и по каждому запросу видно
  полную разбивку: сколько стоил анализ, сколько стоил инструмент, сколько
  стоил финальный ответ.

Это делает LaneGateway ближе к конструктору AI-пайплайнов с прозрачной
экономикой, чем к ещё одному гейтвею для доступа к моделям.

## Как это работает

```
Запрос (бот / CLI / веб)
        │
        ▼
Анализатор (дешёвая/быстрая модель, выбираемая)
  — определяет сложность
  — решает, какие модули нужны (поиск, документы, ...)
        │
        ▼
Модули (SearXNG, документы, ...) — вызываются параллельно, только если нужны
        │
        ▼
Исполнитель (выбираемая "умная" модель) — получает подготовленный контекст
        │
        ▼
Ответ + разбивка стоимости по каждому шагу
```

Каждый шаг этой цепочки — событие с причиной и стоимостью. Это то, что потом
показывается в GUI как "путь решения" запроса.

## Текущий статус

Реализовано (Core + начало Providers):

- `BaseProvider` — абстрактный интерфейс провайдера (chat/vision/embeddings/
  estimate_cost/supports_*), не завязан на конкретного вендора
- `OpenRouterProvider` — рабочая реализация: каталог моделей, чат, vision,
  прогноз стоимости
- `ProviderRegistry` — регистрация провайдеров без хардкода
- FastAPI-каркас (`/health`, `/chat`), конфиг, логирование, простая
  API-key авторизация, подключение к SQLite
- Базовые тесты на провайдер

В работе / дальше по плану:

1. `app/router/` — двухступенчатая маршрутизация (анализатор → модули →
   исполнитель) с событийным логированием каждого решения
2. Эндпоинт истории решений по запросу (бэкенд для будущего GUI)
3. GUI: сначала просмотр пути решения и стоимости (read-only), затем
   возможность менять правила прямо в интерфейсе
4. Второй провайдер, инструменты (SearXNG и другие), клиенты (CLI →
   Telegram → WebUI)

## Стек

Python, FastAPI, SQLAlchemy/SQLite, httpx. GUI — планируется отдельно
(React), будет читать те же события через API.

## Локальный запуск

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env       # заполнить OPENROUTER_API_KEY
python -m pytest -v
uvicorn app.main:app --reload
```
